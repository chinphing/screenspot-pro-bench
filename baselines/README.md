# 基线（baselines/）

三个基线是**同一任务下机制逐步演进**的三代方案。共用 `bench/` 库，各自只实现"机制"本身。

```bash
python3 baselines/b3_crop_ladder.py --split M1 --backend qwen --runs 5 --tag b3_qwen_M1
```

| 参数 | 说明 |
|---|---|
| `--split` | M1 / M2 / M3（读 `splits/<split>.json`）|
| `--ids` | 逗号分隔样例 id（覆盖 `--split`）|
| `--backend` | `qwen` / `deepseek` |
| `--model` | 覆盖默认模型（默认读 `QW_MODEL` / `DS_MODEL`）|
| `--runs` | 重复次数（建议 5）|
| `--tag` | 结果名前缀 → `baselines/results/raw/<tag>.jsonl` |
| `--max-turns` | 循环轮数上限 |
| `--reasoning-effort` | 思考档位，默认 `none`（⚠️ 不显式关会让 Qwen 慢数十倍）|

## 三个基线的定位

| | 决策者 | 机制 |
|---|---|---|
| **B1** | — | 无循环，一次出框（零智能体参照）|
| **B2** | **模型** | 智能体：原图+放大图，模型自己调 `done()` |
| **B3** | **模型** | 智能体：分阶段 + 只送裁片 + 阶梯扩大视野 |

**→ B2/B3 都是智能体模式（模型用工具自己决定下一步）；B1 是无循环的下界参照。**

---

## ⚠️ 基线是 legacy 脚本的**原样拷贝**，不是重写

这一点很重要——曾经踩过坑：把基线"重写"成更简洁的版本，结果**丢掉了多轮消息历史与工具回执**，
模型看不到自己上一轮报过什么，于是永远不调 `done()`：调用数从 2.68 涨到 5.10，耗时翻倍。

**现在 B2/B3 与 legacy 原始脚本的差异只有 6 处 / 30 行**，全部是结构性适配：

| 改动 | 内容 |
|---|---|
| `sys.path` | 指向仓库根（原来指向脚本所在目录）|
| import ×4 | `harness`/`ds_client`/`qwen_client`/`verify_loop` → `bench.*` |
| CLI ×3 | `--ids`/`--desc-file`/`--tag` 不再 required，改由 `--split`/`--desc-version` 推导 |
| 路径推导 | 描述文件与输出路径改成 `descriptions/<版本>/`、`baselines/results/raw/` |
| 输出路径 | `results/l1/cursorXX_*.jsonl` → `baselines/results/raw/<tag>.jsonl` |
| 循环变量 | `args.ids` → `_ids` |

**`run_one` / `draw_pointer` / `draw_box` / `_i` / `_desc_lines` 五个函数逐字未动**
（用 `ast.unparse` 规范化后逐字符比对验证）。

复核命令：

```bash
diff legacy/ds_cursorZF.py baselines/b3_crop_ladder.py   # 应只有 6 个改动块
diff legacy/ds_cursorZ6.py  baselines/b2_agent_marker.py # 同上
```

### 兼容垫片 `bench/compat/`

为了不改动 legacy 代码就能跑在新结构上，`bench/compat/` 提供了三个**逐字拷贝**的模块：

| 模块 | 来源 | 作用 |
|---|---|---|
| `qwen_client.py` | `legacy/qwen_client.py` | 复刻 `qc.chat` / `qc._b64_png` 等模块级接口 |
| `ds_client.py` | `legacy/ds_client.py` | 复刻 `dc.chat` / `dc.ask_image` / `dc.b64_jpeg` |
| `verify_loop.py` | `legacy/verify_loop.py` | 抽出 `draw_cursor` / `pad_edge` / `L1_PROMPT` 三个符号 |

**刻意不重构、不统一签名**——签名经 `inspect.signature` 比对与 legacy 完全一致。
新代码请用 `bench.clients` 的统一接口；垫片只为基线保真服务。

## B1 —— 单图直出（`b1_direct.py`）

**机制**：整图缩放到 <2.5Mpx → 短提示要 bbox → 一次调用结束。**无循环。**

**用途**：零智能体参照。B2/B3 相对它提升多少，就是机制的价值。

| 后端 | 命中 | ERROR | 单次 | 调用 | 距边 | 擦边 | 失败距离 |
|---|---|---|---|---|---|---|---|
| qwen3.8-flash | **60%** (12/20) | 0 | **1.7s** | 1.00 | 34% (+16%) | 42% (−5%) | 77px |

**→ 60% 是"零智能体"的底：机制价值 = 86% − 60% = 26pp。**

---

## B2 —— 智能体 + 画标记 + done（`b2_agent_marker.py`）

**机制**：**模型**自己决定停不停。
- 第 1 轮：只给**原图**（无标记）→ 模型调 `locate` 报框
- 第 N 轮：给**原图 + 放大裁片**，两张都画出**当前框** → 模型判断"框住了吗"
  · 框住了 → 调 `done()` 结束
  · 没框住 → 调 `locate` 报新框

**两种标记**（`--marker`）：

| 值 | 标记 | 特点 |
|---|---|---|
| `box` | 蓝矩形框 | 大目标更稳 |
| `square` | 框中心小方块（边长 = 框长边×30%，最小 8px）| **小目标更居中** |

| 后端 | 标记 | 命中 | ERROR | 单次 | 调用 | 距边 | 擦边 | 失败距离 |
|---|---|---|---|---|---|---|---|---|
| qwen3.8-flash | square | **86%** (86/100) | 0 | 10.3s | 2.79 | **50% (+71%)** | 30% (−31%) | 161px |

**→ 命中率最高（86%），落点也最居中（距边 50%，全场第一）。**

---

## B3 —— 分阶段 + 只送裁片 + 阶梯（`b3_crop_ladder.py`）★ 当前最优

**机制**：三处结构改动。
1. **分阶段**：阶段 1 用整图 + 短提示（纯文本 bbox）拿粗定位，**不进入工具循环**
2. **校正轮只送裁片**：不再给整图 → 强制模型在小图内报框，比例换算交给脚本
3. **裁片阶梯 200→400→800→1600**：目标不在裁片里就调 `not_visible()` 扩大视野

**为什么"只送裁片"**（诊断数据）：
- 整图 2.5Mpx 时目标只占十几像素 → 报框误差中位 **53px**
- 只给裁片后 → 误差中位降到 **34px**，小目标(<40px)命中率提升最明显

| 后端 | 命中 | ERROR | 单次 | 调用 | 距边 | 擦边 | 失败距离 |
|---|---|---|---|---|---|---|---|
| qwen3.8-flash | **82%** (82/100) | 0 | 7.9s | 2.68 | 36% (+23%) | 30% (−31%) | **87px** |
| deepseek-flash | **74%** (74/100) | 0 | **3.9s** | 2.96 | 36% (+23%) | 36% (−17%) | 248px |
| qwen3.7-flash | 71% (71/100) | 0 | **4.7s** | 2.27 | 43% (+46%) | 32% (−28%) | **39px** |

**→ 跨后端综合最优：DeepSeek 上唯一超过 70% 的机制，且最快（3.9s）。**

**结构对弱模型收益最大**：同一个 qwen3.7-flash，从旧机制（Z4）的 33% 提升到 71%（**+38pp**），
"全错样例"从 10/20 条降到 2/20 条。

### `--out-px`：固定输出边长（推荐 1600）

默认 `--out-px 0` 沿用 legacy 的固定倍率（`--zoom 4`），阶梯四档实际送出
800 / 1600 / 3200 / 6400 像素的裁片。

**但服务端会把单图输入压到 ≈2.5Mpx。** 实测：同一张 6016×3384 的图分别以
20.4 / 10.0 / 5.1 / 2.5 Mpx ��出，前三者返回的 `image_tokens` **完全相同（2481）**，
只有 2.49Mpx 时降到 2444。所以 3200 与 6400 两档**实际拿到的是被压过的图**，
有效放大倍率反而随档位上升而下降。

`--out-px N` 让每档都按固定边长 N 输出（`ZM = N / CP`）。取 **1600** 时：

| 档 | `--out-px 0`（legacy）| `--out-px 1600` |
|---|---|---|
| 200px | 4× | **8×** |
| 400px | ~4× | ~4× |
| 800px | ~2× | ~2× |
| 1600px | ~1× | ~1× |

**差别只在 200px 档（4× → 8×）**——其余档位两种设置本来就等价（都被压到同一上限）。

受控实验（n=100，冻结 L1 起点、逐条配对）：

| 配置 | 命中 | 原失败 50 | 原成功 50 | 单次 |
|---|---|---|---|---|
| `--out-px 0`（legacy）| 57 | 8/50 | 49/50 | 7.8s |
| **`--out-px 1600`** | **63** | **15/50** | 48/50 | **5.5s** |

- n=100 上：精度 **+6pp**（p≈0.39）、耗时 **−30%**

**但 M3 全量（1261 条，同批样本）没有复现：**

| 配置 | 命中 | 单次 | 平均 move |
|---|---|---|---|
| `--out-px 0` | 1049/1261 = **83.2%** | 6.3s | 1.67 |
| `--out-px 1600` | 1056/1261 = **83.7%** | 6.6s | 1.78 |

**+0.6pp（95% 区间 ±2.9pp，z=0.38，p≈0.53），耗时反而 +5%。**

**→ `--out-px 1600` 是中性改动，不推荐作为默认。** n=100 上的 +6pp 是假阳性——
按功效计算，n=100 只能可靠检出 ≥10pp 的差异。

**但它暴露了一个更要紧的问题**：两次运行之间逐条翻转 **125 条**
（弄坏 59 / 修好 66），净变化只有 +7。说明**单次运行的逐条结果噪声很大**，
这直接限制了所有小样本 A/B 的可信度——**在测出噪声底之前，任何 <5pp 的差异都不该当真**。

## ⚠️ 已淘汰：脚本驱动的校验循环（`legacy/b2_verify_loop.py`）

早期还有一代 **脚本驱动**的方案：L1 初定位后，由**脚本**裁片、画方块标记，
问模型「方块在目标上吗」，按回答决定下一步。**已被淘汰**，原因是被 B2/B3 完全支配：

| 方案 | 决策者 | 命中(qwen) | 单次(qwen) | 命中(ds) | 单次(ds) |
|---|---|---|---|---|---|
| 校验循环（旧 B2）| **脚本** | 82% | **18.5s** | 70% | 3.0s |
| 画标记 B2 | 模型 | **86%** | 10.3s | — | — |
| 裁片阶梯 B3 | 模型 | 82% | **7.9s** | **74%** | 3.9s |

- **qwen 上**：同样 82%，但慢 **2.3 倍**（18.5s vs 7.9s）
- **DS 上**：70% < 74%，精度也输

**结论：让模型自己决定下一步（智能体模式）全面优于脚本硬编码流程。**
脚本代码与历史结果保留在 `legacy/b2_verify_loop.py`、`legacy/results_verify_loop/` 供追溯。

## 怎么选

| 场景 | 推荐 | 理由 |
|---|---|---|
| 追求最高命中率 | **B2 `--marker square`** | 86%，落点最居中（距边 50%）|
| 追求速度/成本 | **B3 + deepseek-flash** | 3.9s，74% |
| 均衡 / 跨后端稳定 | **B3** | 双后端都 ≥74%，失败离得最近（87px）|
| 下界参照 | **B1** | 60%，1.7s，无循环 |

**⚠️ 4pp 的差距不显著**：86% vs 82%，SE≈5.2pp，95% CI = 4pp ± 10pp。
**选型时应结合落点质量与耗时，不要只看命中率的排名。**

# 描述文本（descriptions/）

��个样例的「目标元素描述」，是整套评测的**输入**。定位提示词里的"目标元素描述"就来自这里。

## 目录结构（按版本组织）

```
descriptions/
├── v1/                    历史版
│   ├── META.json          版本元信息（生成时间/模型/覆盖范围/说明）
│   └── M1.json            20 条（只有 M1）
└── v2/                    当前版
    ├── META.json
    ├── M1.json            20 条
    ├── M2.json            300 条
    └── M3.json            1261 条
```

## 为什么要有版本

**描述一旦生成就不能可靠地重新生成**——实测（2026-10-16）：

| 样例 | V1（2026-10-15） | 用**原始脚本**重跑（2026-10-16）|
|---|---|---|
| `powerpoint_windows_56` | 红色向右弯曲的箭头符号 | 白色弯曲箭头图标 |
| `origin_windows_1` | 白色矩形，内含三条蓝色水平横线 | 白底黑边正方形，内部有红色画笔符号 |

请求参数完全一致（PNG 编码、`temperature=0`、`max_tokens=200`）——**差异来自模型本身**。
`qwen3.8-flash` 是**浮动别名**，后端模型随供应商更新而漂移。

**→ 所以描述必须冻结成数据、并带版本号。** 评测时直接读取，绝不临时重新生成。

## 两个版本

| 版本 | 覆盖 | 生成时间 | 模型 | 说明 |
|---|---|---|---|---|
| **v1** | **只有 M1**（20 条）| 2026-10-15 04:32 | qwen3.8-flash（旧快照）| `ARCHIVE*.md` 里的 M1 历史成绩（86%/82%/74%）用的就是这一版 |
| **v2** | **M1 + M2 + M3**（1581 条）| 见 `v2/META.json` | qwen3.8-flash（当前）| 三个集合来自同一次生成，口径一致 |

### ⚠️ V1 与 V2 的成绩不可直接比较

两版描述内容不同 ⇒ 同一基线在两版上的成绩不是同一个东西。**横向对比必须锁定同一版。**

### ⚠️ V1 无法为 M2/M3 补齐

V1 只覆盖 M1（当时实验规模小）。模型已漂移，**无法再用同样的方式生成 M2/M3 的 V1 版**。
所以要么整套用 V2，要么 M1 用 V1 而 M2/M3 用 V2——后者会让"在 M1 调参、去 M2 定成绩"的协议失真。
**正式成绩一律用 V2。**

## 怎么用

```bash
# 基线默认读 v2
python3 baselines/b3_crop_ladder.py --split M2 --backend qwen

# 指定版本（复现历史成绩时用 v1）
python3 baselines/b3_crop_ladder.py --split M1 --backend qwen --desc-version v1

# 生成（⚠️ 只在确定要换新版本时执行；会新建一个版本目录）
python3 scripts/gen_descriptions.py --split M2 --workers 8 --desc-version v3
```

**基线结果会自动记录所用版本**：结果行有 `desc_version` 字段，文件名带版本段
（`<基线>_<后端>_<划分>_<版本>[_r<N>].jsonl`），汇总表有「描述版本」列。

## 字段

| 字段 | 来源 | 说明 |
|---|---|---|
| `feat` | 模型（紧裁片，红框标目标）| 外观特征，≤40 字 |
| `ctrl` | 规则推导 | `按钮` / `元素`（由 `feat` 是否含"按钮/图标/按键"决定）|
| `pos` | **纯几何计算** | 5×5 网格档位，如 `屏幕水平【左侧】、垂直【上部】`——不用模型 |
| `env` | 模型（整图+上下文裁片+原始分辨率条带）| 周边锚点，≤30 字；`env_raw` 是校验前的原值 |
| `env_verdict` / `env_issue` | 校验模型（可选，默认关闭）| 实测校验会把正确锚点改错，故默认关闭 |

## 生成质量（V2 小样本抽检，20 条）

| 检查项 | 结果 |
|---|---|
| 锚点句式合规（禁止"位于 X 的左侧"式，要求"X 的某部位"式）| **20/20 合规** |
| 字段完整性 | ✅ 全部有 `feat` + `env` |
| 外观字数 | 中位 26 字（上限 40）|
| 锚点字数 | 中位 17 字（上限 30）|

## 耗时

单条等效约 **13s**（8 并发）→ 1581 条约 **5.7 小时**。
单条耗时波动大（实测 18.8s ~ 216.9s），取决于界面复杂度与模型延迟尖峰。

生成脚本**逐条落盘**，中断后重跑会自动跳过已生成的（`--merge`）。
